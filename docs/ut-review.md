# ut-review の設計の理由と限界

`/ut-review`（コード・文書・方針・計画・LLM への指示に、品質・問題点・課題を洗い出すチェックをかけて報告する）を、なぜこの形にしたか、何ができないかの記録。

## なぜこの名前か
対象を限定しない汎用のコマンドなので、§6 の「単独の動作の名前を許す」に当てはめて `ut-review` とした（候補 8 つと比べ、独立した 2 本のレビューの順位を見て利用者が選んだ。2026-10-14）。
`review` は次の場所でも使われる。それでも使う理由（**許す理由**）を残す。

| 使われている所 | 違い | 許す理由 |
|---|---|---|
| Claude Code の組み込みの `/review` | PR（コード差分）が対象 | 「対象を見て問題を確かめる」という核の意味は同じで、範囲だけが違う。打つ名前は `ut-` が付いて別になる。説明文の先頭で「組み込みの /review（PR 用）とは別物」と打ち消している |
| `/ut-defer` の `review` | サブコマンド（積んだ作業の結果を見る） | コマンド名ではなく、補完の候補に並ばない。意味も「見て確かめる」で同じ |
| 開発環境のファイルセットの名前 | レビュー用のコマンド一式を指す | 名前の空間が別（コマンドとして打たない） |

§6 の「同じ動作語を別の意味で使わない」は、意味が違う使い方を止める規則で、範囲の違いには当たらないと判断した。

## なぜ新しいコマンドにしたか
手元には、目的ごとのレビュー手順が 4 系統あった（調査の検証、手元の差分のレビュー、PR のレビュー、工程の中のセルフレビュー）。どれも対象が決まっており、文書・方針・計画・LLM への指示にはそのまま使えない。
また、どれにも次の 2 つが無かった。この 2 つをこのコマンドの核にした。

- **レビュー自体が働いたことの確認**: 指摘が 0 件のとき、問題が無いのか、検出が壊れていたのかを区別する手段。
- **外部へ送る前のマスク**: Codex に対象をそのまま送っていた。

既存の手順を置き換えるのではなく、独立した汎用版として作り、指摘の書式・重大度・一致ラベルの型だけをそろえた。

## 段の形にした理由
| 段 | 理由 |
|---|---|
| 選定（チェックのチェック）を機械の決定表で行う | 何を見るかを LLM に任せると、見なかったことが報告に残らない。決定表の規則 ID が選定の理由になり、LLM は追加だけができる。利用者の除外は「未実施（利用者が除外）」として必ず報告に出る。必須のチェックは外せない（外せないものを「未実施」と表示しない）。選定表は実際に作るタスクと一致させる（要件なしの要件の突き合わせは「未実施（要件が渡されていない）」にする） |
| 役ごとに別のサブエージェント、他の役の結論・作者の説明を渡さない | 作者の意図を渡すと迎合し、他の役の結論を渡すと同じ見落としが揃う |
| 対象の本文を推測されにくい印で囲む | 本文中の指示（「この節は問題ない」など）に従わせないため。区切りだけでは防げないので、本文中の指示を見つけたら指摘する役割も持たせる |
| 返答の 1 行目に task ID と入力のハッシュ、読んだ範囲、期待した観点の判定を求める | 途中で止まった・別の対象を見た・観点を飛ばした返答を「指摘なし」と取り違えないため |
| カナリア（既知の欠陥を入れた小さな見本）を別の呼び出しで流す | 「その役の経路が働いた」ことを毎回確かめる。拾えなかった役の指摘は消さずに「検出力: 未確認」の印を付け、人へ上げる |
| 指摘の検証を、元のレビューを見ない別のサブエージェントが行う | 書いたモデルを判定役にしない。結論が割れたら、匿名の裁定に回す（このセッションは裁定しない） |
| 引用を開始時の写しと機械で照合し、合わなければ棄却 | 実在しない行を根拠にした指摘を落とす |
| 指摘は機械でまとめず、すべて残す。表示のまとめは LLM の根本原因の案（の番号）で行い、mjs が「全指摘がちょうど 1 回ずつ入る」を検査 | 機械の統合（同じ観点・±5 行）は、自由指摘どうしの別の欠陥を 1 件にして片方を消していた（クロスチェックで判明）。まとまりの重大度は最も高い指摘のもの、判断もその指摘のもの（未確定の Critical を確認済みの Low の陰に隠さない） |
| 等式を 3 つにする（判断: 入力＝確認＋棄却＋未確定、表示: 描いた ID＝棄却以外の ID、予定と実績: 予定＝完了＋未実施） | 表示を件数だけで数えると、判断の等式が成り立てば必ず成り立ち、何も検証しない。予定と実績が無いと、指示を作らずに報告すると「すべて実施」になる |
| 返答はタスクごとのファイルに残し、state.json は accept で書かない。merge の後に受理した返答・Codex の結果があれば report が止まる。返答の無いレビュー・カナリアのタスクがあれば merge が止まる（明示の `--partial` のときだけ、未回答として「未実施」に記録して進める） | 返答を並行して受理すると、同じ状態ファイルの読み書きが競合して先の返答が消える。merge に入っていない指摘を黙って落とさない。返答を待たずに merge すると、未回答のタスクが飛ばされ、読んでいない範囲があることが利用者に伝わらない |
| 網羅性の監査には、Claude の役の読んだ範囲に加えて、Codex のパスごとの status・読んだ範囲・指摘の件数（未実施なら理由）と要件の項目の一覧を渡す | Claude の役の READ だけでは、Codex が未実施・一部しか読んでいないことや、確かめていない要件の項目を監査役が見られない |
| 選んだ Codex を使わない理由は、セッションが `skip-codex --run <ID> --reason <理由>` で残す。残していなければ、部品に分かる事実だけ（mask をしていない／実行していない）を書き、「理由は記録されていない」と添える。アダプタが実行して失敗したときは、アダプタの理由（クレジット切れ・認証切れなど）が優先する | 以前は mask をしていなければ一律に「了承が無い・マスクしていない」と出していた。2026-10-20 にクレジット切れのため Codex を使わなかったときも了承が無いと読め、理由を取り違えた。了承の有無・クレジット・CLI の有無は部品には分からないので、推測で書かない |
| 検証には指摘の前後の行だけを渡す（「無い」という主張はファイル全体）。まとめ・網羅性の監査には本文を渡さない。指摘の一覧・要件・前回の報告も推測されにくい印で囲む | 対象の全文（最大 2 MB）を毎回渡すと分割の上限を超える。対象由来の引用を固定の区切りで指示の領域に入れると、本文に区切りと指示を書くことで持ち込める |
| 作者が確認・検証役が棄却で割れたら、裁定するまで未確定 | 検証役 1 人の棄却で消えると、検証役の誤りがそのまま結論になる |
| 修正の確認（前回の指摘ごとの対応 OK・不十分）と見送りの再審、要件の判定を報告の節に出す。前回の指摘はそのファイルの塊すべてに渡し（関係の無いファイルの塊には渡さない）、要件は項目ごとに ID を固定して全項目の判定を求める。受け持ったタスクがすべて読み終えたときだけ「対応 OK」「満たす」にする。カナリアには「直っていない／直っている」「満たさない／満たす」を 1 つずつ混ぜ、両方を正しく判定したときだけ拾えたとする | 観点の判定にしか無いと報告から消える。前回の行を含む塊だけに渡すと、修正で問題の箇所が後ろの塊へずれたとき、前回の行に別のコードがあるだけで「直った」と読まれ、移った先の塊は前回の指摘を受け取らない（2026-10-19 の再レビュー F110）。該当の箇所の無い塊は「該当箇所なし」と答え（数えない）、関係する箇所があるのに決められない塊は「判定不能」と答える。判定不能は 1 つでもあれば対応 OK にしない（他の塊が該当なしでも。2026-11-12 の再レビュー F079）。該当箇所なしだけが並び該当なしが無いときも、誰も判定していないので判定不能（関係の無いファイルの塊には渡さない）。全部「該当あり」と答えるだけでカナリアを拾えた扱いになる |
| git は差分の変換（textconv）・外部の差分・ファイル監視・hook・フィルタ（filter.名前.clean・smudge・process）を起動しない形で呼ぶ。フィルタは、設定にある名前を読んで、すべて空にし required を外す | 対象リポジトリの設定で、準備のときに対象のスクリプトが実行されうる（「対象のコードを実行しない」に反する）。フィルタは、stat の変わったファイルを index と比べる git status・git diff が起動する（実機で、process を設定した細工リポジトリで確かめた。2026-10-29 の再レビューの指摘 F001。Git LFS のように利用者の環境に普通にある設定でも起動する） |
| 確認済みの件数・人へ上げる項目・対応の候補は、まとまりの中の確認済みの指摘で数える。表示の等式は、書いた md の本文から ID を数える | 未確定の Critical と同じまとまりにある確認済みの High が消えるのを防ぐ。申告した ID で数えると、本文の行が消えても等式が成り立つ |
| 必須の段の時間を先に予約する | 予算切れでカナリア・照合・報告の書き出し・後始末が飛ぶのを防ぐ |
| 段ごとに使えるオプションを決め、知らないオプション・別の段のオプション・同じオプションの 2 回目・値の無い余分な語・値の欠けた／空の値のオプション・`--files` と `--base` の同時指定は、何もする前に exit 2 で止める（Codex のアダプタも同じ。`/ut-defer` の `ALLOWED_OPTS` に倣った）。`prepare` は、入力の検査（「,」だけの `--files`・`--recheck` の無い／形の違う見送りなど）をすべて通してから前回の残りを消す | 以前は黙って無視していた。`--dpeth deep`・`--depth=deep` は標準の深さで、`--files` と `--base` の同時指定は `--base` を捨てて動き、利用者は指定が効いたと思い込む。`--files ""` は差分全体に、`--recheck` の無い `--waivers` はどこにも出ずに消えていた。前回の残りを先に消すと、入力の誤りで止まったときに何を消したかが残らない（2026-10-19 の再レビュー） |
| 直して続けられる止まり方（後の段の入力の誤り・merge の未回答・report の merge の前後）は、出力の最後の行に「直して続ける（cleanup しない…）」の印を付ける | 手順書の表に止まり方を列挙すると、表に無い止まり方（report の「merge をしていない」など）が片付けの側に入り、受理した返答・Codex の結果を消していた（2026-10-19 の再レビュー） |

## 差分の周辺だけを見る（`--scope diff`。差分のときの既定）
以前は差分を対象にしても、変えたファイルを全体で渡していた。1 行だけ変えた大きなファイルが丸ごと渡り、範囲の外の指摘と費用が増えていた（2026-10-16 の再レビューで 9 ファイル・5,974 行・30 タスク）。そこで差分のときは、差分のある行の周辺だけを渡す（2026-10-19、利用者が選択）。全体を見るときは `--scope file`（`--depth` と同じ「値を選ぶ」形。将来 `--scope function` などを足せる）。`--files` の対象は常に全体。

| 決めたこと | 理由 |
|---|---|
| 窓は差分のある行の前後 N 行（`limits.diffContextLines`、既定 30）。重なり・隣り合う窓は 1 つにし、1 ≤ 開始 ≤ 終了 ≤ 行数 に切る | 決定表の数字 1 つで決まり、試験で再現できる（関数の境目は見ない。限界に書いた）。0 以上 1000 以下の整数でなければ決定表の検査で止める |
| 削除だけの塊は削除した所の直前の行（先頭の削除は 1 行目）、未追跡の新しいファイルは全行 | git の `+c,0` の c は削除の直前の行（先頭なら 0）。未追跡は git diff に行が出ない |
| 行の差分を取れない（git の失敗）・読めない（git の出力に hunk の見出しが無い）ファイルは全体を渡し、「未実施」に理由を出す。hunk 0 件（モード変更など）は内容の差分なしとして理由つきで対象外。空のファイルも対象外（窓は []）。git の差分は `--no-color`・`--text` で取る | 失敗と 0 件を同じ扱いにすると、範囲と費用が急に広がり、障害が隠れる（Codex のクロスチェック #7）。`changed` は実際の差分のまま（失敗は不明の null）、全体に広げた理由は別のフィールドに持つ。窓 null（全体）と []（見る行が無い）は取り違えない。利用者の色の設定（`color.ui`・`color.diff=always`）でパイプ先にも色の制御文字が付く、`.gitattributes` の `binary`・`-diff` で「Binary files … differ」だけになる、のどちらでも hunk を読めず、変えたファイルが「内容の差分が無い」として黙って外れていた（2026-10-19 の再レビュー） |
| 1 つのファイルの複数の窓は、同じ `file=` の別のブロックにし、見出しに `of=<全体の行数>` を付ける（ファイルの一部の塊すべて） | 渡した範囲がファイルの一部であることを読み手に示す |
| 見出し・END の行の分も、1 回に渡す量に数える（実際の見出しの文字列の UTF-8 バイト数。見積もりと実際の指示で同じ処理） | 窓が多いと見出しの分が無視できない。固定の見積もりでは上限を保証できない（#9） |
| 要件の突き合わせの役はファイル全体、修正の確認の役は前回の指摘があるファイルの全体を渡す | 窓だけでは「満たす」の根拠が範囲の外にありえ、判定不能が成功に紛れる（#3）。前回の行は修正でずれるので、行の窓を足すと外れる（#6。前回のファイルが今回の対象に無ければ、今の扱いのまま判定なし） |
| 役と Codex への指示は「範囲を重点に読む。範囲外の問題も報告してよい（範囲外として扱われ、検証されない）」。指示の文は手引きの節に置く（Claude の役は `scope:diff`、Codex は `codex:scope`。部品は範囲の一覧だけを差し込む）。Codex には写しをファイル全体のまま置き、対象の行の範囲だけを伝える。読んでいない範囲は渡した範囲を基準に数える（Claude の役と Codex で同じ算法） | 「範囲の行に限る」と指示すると、範囲外の重大な問題が報告されなくなる（#2） |
| 範囲外＝窓の外の行を指す指摘（ファイル全体を渡した役の指摘は除く）。申告の行と、前後 3 行で引用に当たる行がすべて窓の外のときだけ範囲外にし、どれかが窓の中なら範囲の中に倒す（検証にかかる）。引用の照合が先で、引用が実在しない指摘は範囲外にせず棄却する（範囲外は引用が実在したものだけ） | 引用の補正（±3 行）で窓の境目をまたぐ指摘を、黙って検証から外さない（#5） |
| 範囲外の指摘は検証・まとめにかけず、判断は未確定のまま、報告の「範囲外の指摘」の節に 1 件ずつ出す。範囲外の Critical・High は人へ上げる | 範囲の外の前提は見ていないので、確かめた指摘として扱えない。重いものは人が見る |
| 範囲外は判断とは別の軸（`outOfScope`）。判断の等式は 入力＝確認＋棄却＋未確定 のまま、範囲外は未確定の内訳として示し（二重に数えない）、範囲外なのに確認・棄却になった指摘は止める。表示の等式は、表＝棄却でも範囲外でもない指摘、範囲外の節＝範囲外の指摘、で本文から数える | 範囲外を 4 つ目の判断にすると、報告の JSON を使う側（題材集の採点）が壊れる。範囲外を未確定に含めたまま採点すると、範囲を絞っただけで採点が上がる（#1）ので、`tools/ut-review-bench.mjs` の採点は範囲外を命中に数えない |
| 「未実施」には「範囲の外の計 X 行はレビューの対象にしていない（検証・Codex は一部を読みうる）」と書き、網羅性の監査には渡した範囲を伝える。「その役はファイル全体を読む」の注記は、実施した役だけ、修正の確認は前回の指摘があるファイルだけに付ける（報告のまとめ・未実施・監査で同じ式） | 検証は指摘の前後 15 行、Codex は写しの全文を読みうるので、「見ていない」とは断定できない（追加1）。監査役が、範囲の外を読んでいないこと自体を欠けと数えないように |
| `--files` を使わない結合試験（git の差分 → prepare → tasks → 偽の codex → merge → verify → report → 題材集の採点。複数の窓・削除・git の失敗・hunk 0 件） | 部品の試験だけでは、既定の経路の結合が保証されない（追加6。`[X33]`） |

## Codex への送信
- 送るのはマスク済みの写しだけで、毎回の了承の後だけ。了承の画面に出した写しのハッシュを、作業場所に実際に置いた写しで取り直して比べ、違えば送らない。
- マスクは本文とファイル名の両方にかける（伏せる語・型に当たった部分だけを伏字にし、当たらない名前はそのまま。対応表は手元に残す）。鍵の名前は残して値だけを伏せる。この PC のユーザー名は自動で伏せる。`--none` でも型のマスクと陽性対照（型のすべてがどれかの見本で検出されること）は必ず行う。伏せる語の照合は 1 文字ずつ NFKC にして探すが、本文そのものは正規化しない（コードの意味を変えない）。語のファイルが UTF-8 で読めなければ止める。
- 写しだけを置いた空の作業場所を、OS の一時フォルダに作る（伏字前の写しがある実行フォルダの隣に置かない）。離すのは、作業場所に置くものを了承した写しだけにするため（取り違えと、対象の `AGENTS.md` の読み込みを防ぐ）で、**Codex の作業場所の外の読み取りを止める仕組みではない**（`--sandbox read-only` は書き込みを止める指定。実機の結果は「限界」）。そのため、了承の画面に読み取りの範囲（`mask` の出力の `codexReadScope`）を示し、Codex に送った実行では、外の参照が 0 件でも報告の「先に見ること」・まとめ・外の参照の節に件数を出す（0 件は外を読んでいないことを意味しない）。送ったかは Codex の結果の `sent` で決め、送る前に止まった実行には出さない。読み取りだけの sandbox で、利用者の設定・プラグインを読まずに起動する。実行の記録から、作業場所の外を指したコマンド（境界つきで判定。単独の `..`・ドライブ名なしのルート・環境変数も）を拾って報告に出す（1 つのコマンドで当たった外の参照はすべて記録する。UNC は、前が行頭・空白・引用符などで、`\\` の直後がホスト名、その後ろの `\` に `\` が続かないものだけにする。`node -e` の `'\\nA\\n'` のような書式文字列を UNC と誤検出し、その陰に本当の外の参照が隠れていたため）。
- 外の参照の拾い方（2026-10-16 の見直し）: ドライブ名は前が英数字でないものだけ（`https://` の `s://` を外と数えていた）。UNC は `//host/`・`\\?\UNC\`・ASCII 以外のホスト名・JS の文字列の中でエスケープした `\\\\host\\` も拾い、`,`・`:` の後ろ（`a.js,\\srv\s`・`-Path:\\srv\s`）も拾う。ドライブ名なしのルートは 1 段（`/flag`・`\secret.txt`・`\`）も拾い、作業場所の中かを確かめる（POSIX の作業場所では `/` で始まるパス、Windows では作業場所のドライブで解決する）。変数の名前（`$home`・`$Env:`）は大文字小文字を区別しない。`command` が配列の出来事は結合して調べ、文字列でも配列でもないものは「判定できなかった出来事 N 件」として報告に出す（黙って飛ばすと 0 件が「外を読んでいない」と読まれるため）。
- 外の参照は全件を報告の JSON（`outsideReads`）と md の「Codex が作業場所の外を指した参照」に残し、絶対パス・UNC で外と確かめたものを、パスをまたいで先に並べる（実行フォルダの記録は後始末で消えるため、先頭 3 件だけでは 4 件目以降が誰にも確かめられなかった）。確度は、アダプタが絶対パスを作業場所に照らして外と確かめた結果（`outsideSure`）で決める（文字列の形だけで推すと、ドライブ名なしのルート・POSIX の絶対パスが、確かめてあるのに［要確認］に回っていた）。参照とコマンドは切らずに記録し、表示だけ切る。同じ参照はコマンドをまたいでも 1 回に数え、件数は「参照 N 件（M 回のコマンドから）」と書く（コマンドの数と取り違えないように）。
- 外の参照の拾い方（2026-10-17 の見直し）: `\` の後ろがすべて `n`・`r`・`t`・`0` で始まる形を書式文字列として外すのは、文字列の中（`pwsh -Command "…"` のような包みの引用符は数えない）にあるときだけにした（文字列の外の `\temp\notes.txt`・`\tmp` まで捨てていた）。ルートの `\` だけのものは、後ろが引用符なら拾わない（`node -e \"…\"` のエスケープした引用符を外の参照と数えていた。実際の実行で記録された誤検出）。`-Path:..\x`・`-Path:~\x`・`cd ~; gc .ssh\id_rsa`・`${HOME}` も拾う。コマンドは `item.id`（古い形式は `call_id`）で 1 回に数え（Codex CLI 0.154.0 の `codex exec --json` は `item.started` と `item.completed` の両方に command を載せる）、`exec_command_end`・`exec_command_output_delta` は判定できない出来事に数えない。読んだ範囲を返して完走したのにコマンドの出来事を 1 件も見分けられなければ、記録の形が変わった疑いとして「先に見ること」に出す（0 件を「外を読んでいない」と読ませない）。
- Codex が作業場所の絶対パスで返した指摘・READ は送ったパスに戻す。戻せないパスの指摘は、棄却ではなく未確定にして人へ上げる（引用の照合ができないだけで、指摘が誤りとは言えない）。READ の申告はファイルの行の範囲で丸め、逆転・範囲の外だけの申告は使わずに報告に出す（Claude の役の read も同じ条件。部品の `usableRead`・`readProblems` を共有する）。1 つのファイルに範囲が複数あるときは範囲ごとに READ 行を書かせ、「READ <ファイル> a-b, c-d」と並べた行も範囲ごとに分けて読む（以前は書式が「ファイルごとに 1 行」で、並べた行はファイル名の一部と読まれ、窓が両方とも読んでいない範囲になっていた）。送る直前に「送った（結果はまだ無い）」の記録を書き、終わったら結果で置き換える（送った後にアダプタが強制終了されても、報告が「実行していない」と書かない）。起動そのものに失敗したとき（ENOBUFS など）は、終了コード（null）ではなく失敗の理由を記録する。Codex CLI の場所は絶対パスにしてから確かめて起動する（相対パスは作業場所から解決されて起動に失敗していた）。作業場所は作った直後に実パス（8.3 形式・ジャンクションを解いた形）にそろえ、Codex に渡すパス・外の参照の判定・パスの戻しで同じものを使う。
- 写しは作業場所の下のフォルダ（`t/`）に置き、`project_doc_max_bytes=0` を指定する（対象の `AGENTS.md` を Codex がプロジェクトの指示として読み込まないように）。時間切れのときは、包みのプロセスがツリーごと止める（Windows では、子を止めても孫の Codex 本体が残り、出力のパイプが閉じるまで待ち続けるため。`taskkill /T /F`）。Windows 以外では直接の子（codex.js）だけを止める（孫が残りうる。限界に書いた）。強制終了で残った作業場所は、次の `prepare` が消す。
- マスクの範囲は、伏せる語も型も元の本文で求めてから一度に置き換える（伏せる語に `password` のような鍵の名前があると、先に名前が消えて値が型に当たらなくなるため）。引用符で囲まれた値は、閉じる引用符まで（空白・`;` を含めて）伏せる。文字列の中にエスケープして書いた JSON（`{\"token\": \"…\"}`・`\\"`・`\'`）も、名前の後ろと値の両側の「`\` の並び＋引用符」を引用符として扱って伏せる（以前は名前の後ろの `\"` が区切りに当たらず、伏せず・再検査も 0 件のまま送っていた）。値が伏字で始まるときは、伏字の後ろに英数字から続く生の値があるときだけ残りとする（`\n`・`.trim()`・`+x` が続くだけで止めない）。伏せる語は、結合文字・半角の濁点を含めて 1 文字にまとめてから照合する。陽性対照は、秘密の値そのものが消えたことまで確かめる。
- マスクをやり直した後は、前の写しへの Codex の結果を使わない（引用の照合の相手が違うため。未実施として報告に出す）。merge の後に mask をやり直したときは、report が止まって merge からやり直させる（統合のときのマスクを記録して比べる。返答のハッシュだけでは、前の写しへの結果が統合に入ったまま報告されていた）。
- 呼び出しごとに task ID を変え、前回の出力を消してから起動する（前回の出力を今回の完走と取り違えない）。失敗の分類は、失敗したときだけ、エラーの出来事と標準エラーで行う（対象の本文に 401 などがあっても誤って分類しない）。形の誤った指摘の行は捨てずに数えて報告に出す。Codex の返すパスの表記ゆれ（`\`・`./`・大文字小文字）はそろえる。
- Codex にも読んだ範囲（READ 行）を返させ、1 行も無ければ「未実施」、読んでいない範囲は報告に出す。さらに、架空のカナリアを 1 ファイル、普通の名前で同じ作業フォルダに置く（どれがカナリアかは伝えない。指摘は採点だけに使う）。拾えなければ人へ上げ、Codex だけの指摘は「検出力: 未確認」にする。Claude 側と違って別の呼び出しにしないのは、送信の回数を増やさないため（2026-10-14、利用者が選択）。代わりに、カナリアと対象が同じ文脈に入る。そのため、カナリアの置き方が対象の読み方に影響しうる（採点の独立性は下がる）。補う手当てとして、カナリアは採点だけに使い、指摘には入れず、拾えなければ人へ上げる。Codex だけの指摘は「検出力: 未確認」とする。
- 実機の題材集で、Codex が指摘 0 件・印だけを返したことがあった。READ 行もカナリアも無いと、それが「見て問題が無かった」のか「見ていない」のかを区別できない
- 伏字の行への Codex の指摘は、元の本文では引用が合わないので、マスク済みの写しで照合する。伏字にしても行数は変えない（行番号がずれないように）
- 出力の 1 行目（task ID と入力のハッシュ）と最後の行（終わりの印）がそろわなければ「未実施」にする。読み取りだけの設定が無いと全コマンドが失敗したまま exit 0・指摘なしで終わることがあるため、exit 0 だけでは完了としない。
- クレジット切れ・利用制限・認証切れ・CLI が無い・時間切れは「Codex: 未実施（理由）」として、Claude だけで続ける。

## 入れなかったもの
| 案 | 理由 |
|---|---|
| 数値の確信度による足切り | LLM の確信度は較正されていない。判断は 確認・棄却・未確定 の 3 つにした |
| 討論・多数決 | 同じ系統のモデルは誤りが相関し、多数が同じ誤りに揃う |
| 件数の上限で指摘を捨てる | 上限を超えた指摘も ID・原文を残し、「未確定（上限）」として等式に入れる |
| 対象の修正・テストの実行 | 報告だけにした。対応は報告の最後の候補から、大きなものは `/ut-plan` へ渡す |
| Codex の読み取りを、権限プロファイル・elevated・MXC で作業場所に絞る | 2026-10-18 の実機（Codex CLI 0.154.0・この PC）で、elevated＋`-c` で渡した権限プロファイルの指定でも外を読めた（プロファイルが適用されたかは確かめていない）。`mxc` はこの版では `windows.sandbox` の値として受け付けられなかった。読み取りを止められると確かめられた方式が無いので、明記と事後の検出にした（2026-10-19、利用者が選択） |
| 別の利用者・WSL・コンテナで Codex を動かして隔離する | 準備と配布の手間が大きい（利用者ごとの環境の用意が要る）。明記と事後の検出にした |

第 2 版の候補（自己整合性・理解度テスト・数字の照合・敵対的プロンプト）は、題材集で初版の検出の再現率を測ってから足す。

## 検証の仕組み
- 部品の `--selftest`（`ut-review.mjs`・`ut-review-codex.mjs`。Codex の側は偽の codex で動かす）。結果は「N 件中 P 件パス / F 件失敗 / S 件省略」で、Windows でだけ試す試験・手順書や題材集が無い場所（配備先など）で省く試験は「省略」として数え、パスに入れない（理由は SKIP の行。以前はパスに数えていた）。全件省略または試験 0 件は、検証を実施していないため終了コード 1 にする。部品の試験は、手順書と設計の記録に書いた数字（差分の窓の幅・前回の残りを消すまでの時間）が決定表の値と出所つきで一致するかも見る（`[V65]`）。
- `tools/ut-review-sweep.mjs`: 防御を 1 つずつ壊し、その防御を見る試験で落ちるかを確かめる。決定表は、JSON として読んだ規則を 1 つずつ消す（各規則に、その規則だけが選ぶ入力を試験に持たせている。規則の数と変異の数が合わなければ止める）。基準実行は変異と同じ並列の数で同時に走らせる（時間で判定する試験が、負荷の下でも通ることを先に確かめる）。終了コードは 0 全件 CAUGHT／1 それ以外／2 部分実行（`UT_SWEEP_ONLY`）で選んだものが全件 CAUGHT。差し込み位置と、後から当てる置き換えは、どちらも一致がちょうど 1 件であることを確かめる（後から当てる置き換えが黙って何もしないと、意図より弱い変異のまま結果が出る。2026-10-20 に、2 件がこの状態だったのを見つけて直した）。`UT_SWEEP_CHECK=1` で、selftest を走らせずに差し込み位置だけを確かめる。手順書と設計の記録も写しに入れ、変異の対象にする。一時フォルダは正常終了・例外・中断（SIGINT・SIGTERM・SIGHUP・SIGBREAK）で消す（強制終了では残る）。
- `tools/ut-review-bench.mjs`: 欠陥を仕込んだ架空の題材（コード・報告・計画・方針・LLM への指示・設定）で、選定の再現率（機械）と、実際に流した報告の検出の再現率（命中＝判断が確認か未確定で、ファイル・行・説明（筋書き・直し方。引用は数えない）が合う。範囲外の指摘は数えない）を測る。

実測（2026-10-15、2 回目のクロスチェックの修正を入れた版。standard・Codex 観点なし 1 回。差分の周辺だけを渡す `--scope diff`（2026-10-19 から差分のときの既定）を入れる前の版で、題材は `--files` で渡す（ファイル全体）。`--scope diff` での検出の再現率は測っていない。採点は、引用の語も鍵語に数えていた版（2026-10-20 から筋書き・直し方だけ）による）:

## 限界（保証しないもの）
- **LLM が行う判断の質**（ペルソナ・検証・裁定・網羅性の監査）は、部品の試験では保証しない。題材集の検出の再現率で、実行ごとに測る。カナリアが確かめるのは経路が働いたことで、検出力そのものではない。
- 検証役も同じ系統のモデルなので、同じ見落としをすることがある。Codex を使っても誤りは相関する。
- マスクは、伏せる語の一覧と機微値の型で行う。一覧に無い固有名詞・未知の形式の秘密・コードそのものの機密は守れない。了承の画面でマスク後の写しを人が確かめる前提にしている。
- 報告には対象の引用が入る。報告はローカルに残し、外へは送らない（共有の前に人が確かめる）。
- 対象の変化は、開始時と終了時の目録（パス・サイズ・ハッシュ）と `git status` で見る。間で変えて元に戻した場合は検出しない。
- シンボリックリンク・ジャンクション（とその下）・バイナリ・上限を超えるファイル・削除されたファイル・自動で飛ばすディレクトリ（bin・dist など）は対象外として理由つきで列挙し、中身は見ない。削除そのもの（消したことの是非）はレビューしない。
- 1 行だけで 1 回に渡せる量の上限を超える行があるファイル（minify したコード・1 行の JSON など）は、行の途中では分けられないので対象外にする（理由と行番号を報告に出す）。
- 大文字小文字だけが違う別のファイル（大文字小文字を区別する FS の `A.js` と `a.js`）は、後の方を理由つきで対象外にする（パスの照合とマスクの送るパスが大文字小文字を区別しないため）。区別しない FS で同じファイルを 2 通りに指定したときは 1 つにする。
- `[V70]`（フィルタを動かさない）は、防御を付けない `git status`・`git diff` が設定のフィルタを動かすことを先に確かめる。動かない環境では判定不能として省略（skip）に数える。
- `[V29]`（textconv を動かさない）は、同じ設定で `--no-textconv` を付けない `git diff` が textconv を動かすことを先に確かめる。動かない環境では判定不能として落ちる。
- Codex には作業場所のパスが送られる。既定の OS の一時フォルダはユーザー名を含みうる（報告に出す。避けるなら `UT_REVIEW_CODEX_TMP`）。
- 本ツールは Codex の作業場所の外の読み取りを止めない（遮断を保証しない）。マスクが守るのは、作業場所に置いて渡す写しだけで、Codex が外を読めば、伏字前の内容（対象の元のファイル、実行フォルダの `snapshot/`・`tasks/T*.txt`・`state.json` など）も読まれうる。外の参照の検出は事後の、コマンドの文字列の形からの推定で、文字列にパスが出ない読み方は拾えない（0 件は外を読んでいないことを意味しない）。実機の確かめ（2026-10-18・Codex CLI 0.154.0・この PC（Windows 11）。作業場所の外に無害な印のファイルを置き、その中身を返させた）:
  | 試験 | 指定した値 | 結果 |
  |---|---|---|
  | A | 今の起動と同じ（`windows.sandbox="unelevated"`・`--sandbox read-only`・`--ignore-user-config` ほか） | 作業場所の外を読めた |
  | B | `--sandbox` を外し、`windows.sandbox="elevated"` と、作業場所だけを読める権限プロファイル（`default_permissions`・`permissions.<名前>.filesystem`）を `-c` で渡す | 作業場所の外を読めた。`-c` で渡したプロファイルが効かないのか、elevated で読み取りを止められないのかは切り分けていない |
  | C | B の `elevated` を `mxc` に | この版では設定の値として受け付けられず、起動しなかった（外部へは送っていない） |

  別の版・別の環境・別の指定での挙動は確かめていない。
- 機微値の型は正規表現なので、値が 6 文字未満の代入・型に無い形式は伏せない。逆に、コードの `token = getToken()` のような代入も伏せることがある（安全側）。伏字の後ろに英数字以外（`+`・`/`・`-` など）から始まる生の値が残っても、残りとしては拾わない（マスクは値を区切りまで丸ごと伏せるので、マスク自体からはこの形は生じない。対象に元から伏字が書かれているときだけ起こりうる）。閉じの引用符が無いエスケープした値（`\"abc…` で行が終わる）は伏せない。
- Codex の外の参照は、コマンドの文字列の形から推し量る（実際にどのファイルを開いたかは見ていない）。拾わない・誤って拾う形が残る:
  - `\` の後ろがすべて `n`・`r`・`t`・`0` で始まるドライブ名なしのパスは、文字列の中にあると（`type "\temp\new"`・`pwsh -Command "type '\temp\new'"`）、1 本の `\` の書式文字列（`'\nfoo\n'`）と区別できないので拾わない（文字列の外の `\temp\new` は拾う）。文字列の中かは、`'`・`"` と、`\` を前に置いた `\'`・`\"` を別の種類として開き・閉じを数えて決め、シェルに渡す包み（`pwsh -Command "…"`・`bash -lc '…'`・`cmd /c "…"`）の引用符は数えない（`pwsh -Command "type \temp\new"` は拾う）。引用符の対応が崩れたコマンドでは、外の参照を書式文字列として捨てることがある。
  - ルートの `\` だけのものは、後ろが引用符なら拾わない（`dir "\"` のような形は拾わない）。
  - `~` は、前が空白・引用符・`(`・`,`・`:` で、後ろが区切り・空白・`;` などのものを拾う。`rg "~" t` のような、パスでない `~` も拾うことがある（［要確認］として並ぶ）。
  - `/` の 1 段は、オプション（`cmd /c`）と区別するため 3 文字以上か `.` を含むものだけを拾う（`/x` は拾わず、`start /min` の `/min` は拾う）。`ls /` のような `/` だけのものは、式の割り算（`x / 0`）と区別できないので拾わない。
  - 前が英数字のドライブ名（`aC:\x`）・コロンの後ろの `//`（`file:///etc/x`）は拾わない。前が引用符の `'a:\nb'` のような書式文字列は、ドライブ名つきのパスとして拾うことがある。
  - `..` と変数の参照は、作業場所の中かを確かめられないので常に外と数える。同じ参照をコマンドをまたいで 1 回にまとめるため、2 つ目以降のコマンドは記録に残らない（最初のコマンドだけを添える）。
  - パスの区切りに `,` を使うので、`,` を含むファイル名は `,` の手前で切れる。
- Codex の自己テストは偽の codex で行う。実物では題材集で、完走の印・READ 行・カナリアが働くことを確かめた。起動の指定は CLI の版で変わりうるので、版を上げたら `codex exec --help` と照らす。時間切れのときのツリーごとの停止は偽の codex（応答しない）で試験した。孫のプロセスが本物の Codex 本体のときの挙動は、決定的に起こせないため試験していない。Windows 以外では、時間切れで止めるのは直接の子（codex.js）だけで、孫（Codex 本体）が残って処理を続けたり、出力のパイプを持ち続けたりしうる（プロセスのグループごと止める形は入れていない）。
- 最後の動き（state.json・返答・作業フォルダの更新）から決定表の `limits.staleIdleHours`（既定 72）時間を超えた作業フォルダは、止まり方を問わず（了承待ちも、直して続ける止まり方のまま置いたものも）次の `prepare` が消す（消された実行に続けて段を打つと止まり、受理した返答・merge・検証の結果は失われる）。
- 差分の周辺だけを見るとき（`--scope diff`。差分のときの既定）の限界:
  - 窓は差分のある行の前後 N 行（決定表の `limits.diffContextLines`、既定 30）の決まった幅で、関数・節の境目を見ない。範囲の外の定義・呼び出し元・設定に依存する問題は、役に見えない（指示では未確定・判定不能にさせる）。「無い」という主張（呼び出し元が無い・手当てが無い）にも弱い。
  - 範囲外の指摘は検証しない。変更した箇所（窓の中）と問題が現れる箇所（窓の外）を分けて扱う仕組みは入れなかった（複雑さのため。Codex のクロスチェック #2）。範囲の外の重大な問題は、範囲外の Critical・High として人へ上げるだけ。全体を確かめるなら `--scope file`。
  - 選定に使う特徴（不可逆な操作・外部とのやりとり・数字）は、窓ではなくファイルの全文から取る。窓に関係しない役が選ばれ、費用が増えることがある（選ぶ側に倒した。#4）。1 行だけで 1 回に渡せる量を超える行も全文で見るので、窓の外にそういう行があると、小さな差分でもそのファイルは対象外になる（理由と行番号は報告に出る。追加5）。
  - 削除した行の中身は、どの役にも渡さない（今の版に無いため。ファイル全体のときも同じ既存の限界）。削除だけの塊は、見出しに「削除: N 行目の後で M 行」と出し、手引きで「消えた処理が無いか」を前後の行から確かめさせる（2026-10-19、利用者が選択。中身を別に渡す案は、量・引用の照合・Codex に送るときのマスクを作り直す必要があるので採らなかった）。
  - 差分の行を取った後、本文を読むまでの間に対象が変わると、窓の行がずれる。開始時と終了時の目録の比較で検知する範囲にとどまる（追加3）。
  - カナリアにも同じ前置き（手引きの scope:diff）と範囲（1〜全行）を付けるが、ファイル全体の塊として渡るので、ファイルの一部の塊（`of=` 付き）と見分けられうる。カナリアを拾えたことは経路が働いたことの確認で、範囲の網羅の証明にはしない（#8）。
- サブエージェントが使えない環境（Codex から呼んだときなど）では動かない（未実施と報告して止まる）。
