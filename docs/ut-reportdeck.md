# ut-reportdeck の設計の理由と限界

`/ut-reportdeck`（正本から、プレゼン用の資料を縦に読む 1 ファイルの HTML として作る）を、なぜこの形にしたか、何ができないかの記録。

## なぜこの名前か
`ut-<対象領域><成果物>` の形で、対象は主な入力である `/ut-report` の報告、成果物は会議で使う資料（deck）。補完で `/ut-report` の隣に並ぶ。
候補（`ut-deck`・`ut-docdeck`・`ut-reportbrief`・`ut-docbrief`・`ut-onepager`・`ut-present`）と比べ、独立した 2 本のレビュー（規則の観点・利用者の観点）がどちらもこの名前を 1 位とした（2026-10-13）。
- `deck` からは PowerPoint やスライド送りを期待されうるため、説明文で「縦に読む 1 ファイルの HTML（PowerPoint ではない）」と打ち消している。PowerPoint の書き出しを足すなら、別のコマンドではなくこのコマンドの指定として足す
- `brief` は「短い要約」に読めるため使わない（要約版を作るなら、その名前として取っておく）
- `report` は `ut-alertreport`・`ut-diskreport` では成果物の位置にあり、ここでは入力の位置にある。語の意味（報告書）は同じなので、§6 の「同じ動作語を別の意味で使わない」には当たらないと判断した使い方はコマンド本文と `commands/templates/ut-reportdeck-guide.txt`。

## なぜ新しいコマンドにしたか
一次報告（調査結果の記録）とプレゼン（会議・新規参画者・上長に見せる資料）は、目的・読み手・構成が違う。

| 案 | 判断 |
|---|---|
| `/ut-report` の既定を変える | 採らない。一次報告の使い方（記録としての 10 章）が崩れる |
| `/ut-report` に形式のオプションを足す | 採らない。2 つの目的が 1 本に混ざり、指示が倍近くに長くなる |
| `/ut-docrewrite` に入れる | 採らない。「元の文書を全面的に書き直す」と「元を残して別の資料を作る」が混ざる |
| **新しいコマンド** | 採る。「正本 → 別資料としてのプレゼン版」という実際の流れと同じで、責務が分かれる |

`/ut-report` には、どちらにも効く 2 点だけを入れた（図を外部から読み込まない、伏字の後でも文が成り立つように書く）。

## なぜ検証を別の工程にしたか
実際にプレゼン版を作ったとき、見やすさの多くは作り方（構成表・1 ページの型・図の作法）から来たが、**正確さのほとんどは第三者の検証で直したもの**だった。作成者は自分の推論を足し、限定を落とし、比べる期間を都合よく絞る。これは作成者のセルフレビューでは見つかりにくい（手引きの §9 の 8 つの型）。
そのため、検証は読み取りだけのサブエージェントに分け、照合した件数を build が出す数字の件数と突き合わせる（読めなかった・一部しか見なかったのを「指摘なし」と取り違えないため）。

## 機械の検査を build に入れた理由
マスク漏れと外部読み込みは、目視では見落とす。build は書き出す前に検査し、外れたら何も書かない。
- **マスク漏れ**は、トークンとは別の「伏せる語の一覧」で見る。トークンの左側から語を取ると、包み忘れた語（見出し、図の軸、表、title）が検査の対象に入らず、「実名版で語が見つかる」も作りから当然で陽性対照にならないため。
- どの検査も、毎回、わざと問題を入れた見本で検出できることを確かめてから使う（0 件を正常と読まない）。

## なぜ資料に「型」を持たせたか
機械の検査が通っても、構成が読み手に合わないと「分かりにくい」と差し戻された（障害の資料で、結論が事象の説明だけになった例が最初）。構成の分かりやすさは機械では測れないので、**型を決めて、型ごとの必須の章を build が検査する**ことにした。
- 型は 4 つ（決裁・提案／障害・不具合／調査報告／読本・解説）。**読み手が読んだ後に何をするか**で選ぶ。型を増やすと、選び間違いと保守（自己試験・掃引・理解度テスト）の費用が増えるので、まず少数にした。早見表や一覧は独立した型にせず、付録にする。
- 選ぶのは**利用者**。構成表の先頭に「型と理由」を載せて承認を取る。型をモデルが黙って決めると、間違っても検査は通り、読みにくい資料だけが残る（エラーを出さずに失敗する型）。
- 型は `/ut-report`（正本）と共通。プレゼン版は正本に無い主張を足せないので、型が要る節（例: 決裁・提案の「案の比較」）の素材が正本に無いときは、資料の側で足さずに止める。
- 考え方の出どころ: 文書の型を読み手の必要で分けて混ぜないという整理（Diátaxis）、結論先行（Minto）、障害の事後報告・判断文書の定型。いずれも検索で得た要約と一般的な説明に基づき、一次資料は確かめていない。社内の読本・方式比較の資料（20 本）は、構成の作り（主張の見出し・章のゴール・確認の問い・用語表・結論と比較のカード）だけを自分の言葉で取り、文・固有名は写していない。
- 参考資料の弱点（結論が最初に無い・一覧表と通読が 1 冊に混ざる・未確認が末尾に隠れる）は、1 ページ目を結論にする、一覧は付録に回す、決裁の型では未確認も結論の近くに置く、で避けた。
- 進捗バーと外部フォント（参考資料にあった）は、スクリプトと外部読み込みを禁じているので採らない。確認の問いの答えは `<details>` で折りたたむ。

## 外部の改善案を取り込むか決めるとき
AI に資料を作らせる方法を論じた記事や情報に当たったときは、その内容を鵜呑みにせず、次の順で判断する。同じ案に当たるたびに同じ検討を繰り返さないよう、見送った案と理由をここに残す。

1. **案を 1 文にする。**（出所ではなく、「何を変えると良くなる」という案にする）
2. **既にあるかを確かめる。** コマンド本文・手引き・build の検査のどこに同じ働きがあるかを、実物で探す。
3. **反証する。** その案が正しいなら、手元の実際の資料で起きているはずのことを数える。数えて合わなければ採らない。
4. **採否を決める。** 既にある・効果を測れない・誤警告が多い案は採らない。**覆す条件**を書いておく。

### 判断の記録
手元の実際の資料（12 本・186 章）で数えた結果は次のとおり（2026-11 の測定。数えたのは構造だけで、内容は見ていない）。

| 案 | 既にあるか | 反証の結果 | 判断（覆す条件） |
|---|---|---|---|
| 作る前に読み手・場面を確かめ、推測で作り始めない | ある（構成表の了承の前に生成しない。読み手と目的を聞く。手引き §0 は通読か引くかも聞く） | — | 追加なし |
| 内容の制約（資料に無い情報は足さない・順番は元のとおり） | ある（正本に無い数字・主張は足さない。限定の落ち・断定の強まりを第三者が検査） | — | 追加なし。こちらの方が厳しい |
| 1 枚 1 メッセージ | ある（見出しは言いたいことを 1 文。手引き §3） | — | 追加なし |
| 作成後の自己点検 | ある（build の検査・第三者の検証・8 つの型） | — | 追加なし |
| 規則を途中で読み直させる・型を守らせる | 不要（部品が機械で守る。AI の記憶に頼らない） | — | 追加なし |
| 同じ構成のページを 3 枚続けない | ない | 12 本のうち 7 本に、同じ構成の章が 3 つ以上続く所がある（「問題点 1・2・3」のように、報告では自然に並ぶ）。禁止すると過半数で誤警告になる | **採らない**（覆す条件: 同じ構成の連続が原因で読み手が迷った、と理解度テストで 2 回以上出たとき） |
| 箇条書きは 3 つまで | ない | 41 件のうち 33 件が 3 つを超え、20 件は 5 つを超える。それでも理解度テストは通っている | **採らない**（覆す条件: 長い箇条書きが読みにくいという指摘が 2 回以上出たとき） |
| 強調（数字のタイル）の上限 | 実質ある | タイルは 1 章に最大 4 つ、5 つ以上は 0 件。上限を足しても何も変わらない | **採らない**（足しても効果が測れない） |
| 1 ページの文字量の上限 | 本文は 2〜3 文という手引きのみ | 本文の文字数は中央値 129・90 パーセンタイル 416・最大 1694 で、裾が長い。ただし長さと分かりにくさの関係は測れていない | **保留**（覆す条件: 理解度テストで「長すぎて読めない章」が 2 回以上出たら、その章の長さを測って上限を決める） |
| 見本を複数作って選ばせる・色やフォントを選ばせる | 不要（見た目はテンプレートで固定） | — | 流用しない |
| 枚数と発表時間の目安・スライドへの変換 | 対象外（縦に読む 1 ファイルの HTML） | — | 流用しない |

測るときの注意: 「同じ構成」は、図の種類があればそれ、なければ本文の要素の並びで数えた。この数え方を変えると 3 つ続きの件数は変わる。

## 限界（範囲外）
- **正本そのものの誤り**は捕まえない（正本と照合するため）。
- 第三者の検証も同じ系統のモデルなので、同じ見落としをすることがある。理解度テストで外れた所は、人が読んで確かめる。
- Playwright が無い環境では、表示（横のはみ出し・暗いモード）を実際には見ていない。build の静的な検査（viewport・固定幅）だけになり、報告には「表示の検査: 未検査」が出る。
- 図は 0 以上の値だけを扱う（縦軸を 0 から始めるため）。構造図の箱の位置は手で決める（自動の配置はしない）。
- 伏せる語の一覧に無い機微情報（数値の組、言い回し）と、一覧に無い表記の揺れ（姓だけ・ローマ字・異体字）は検出しない。共有する前に人が確かめる。
- スマートフォン幅では図が縮み、図の中の文字は小さくなる（表示の検査も文字の大きさは測らない）。細かい値は図の表で読む前提にしている。
- 一時の名前から正式な名前にする途中でファイルシステムが失敗した場合の戻しは、決定的に起こせないため試験していない（読み直しの照合も同じ）。
- 外部参照の検査は、スキームの無いホスト名（`intra.example.local` のような文字）を見ない。表示の静的な検査は px の固定幅だけを見る（rem・vw などの単位は見ない）。
- 数字の一覧の網羅の照合は、器（テンプレート）と描き方に由来する数字の漏れを捕まえるためのもの（値の集合で比べる）。同じ値が何か所にあるかは、一覧の側で 1 か所ずつ持つ（deck.json の表示される文字列をすべて集める）ことで担保している。
- 器は固定で、差し替えられない（差し替えた器の CSS の書き方によっては、外部参照・固定幅の検査をすり抜けうるため）。
- 小数は 15〜17 桁を超える精度を JSON の読み込みで失う（整数は 2^53 未満に限って受け付け、超えると止める）。
- マスク漏れの照合は、タグを除いて表示の文字を続けた形でも行うため、隣り合う別々の語が偶然つながって伏せる語に一致すると止まる（安全側の誤検出）。
- **実案件での確認は、1 件だけ行った（2026-11-11。障害・不具合の型、既存のマスク済みの一次報告から作り直し）。**build の検査と数字の照合（116 件中 116 件一致）は通ったが、第三者の理解度テストと正本との突き合わせで、**検査では見つからなかった問題**が出た: 構造図の矢印に正本に無い因果を足していた、1 ページ目に読み手へのお願いが無かった、時点が無い、見出しが正本の限定より強い、正本にある担当を「未定」と書いていた。うち、部品の問題（3 件のカードが 2 列で 1 枚だけ残る・凡例に使わない線種が並ぶ）は部品を直し、資料の作り方の問題は手引きに足した。作り直した版の再検証は 1 回で、残る指摘（略語の定義が正本に無い、影響の件数が正本に無い等）は正本の側の課題。人の読み手の評価は含まない。
- **型の効果は、人の読み手では測っていない。** build が見るのは「必須の章があるか」だけで、章の中身が読み手に合うかは見ない。型の選び方の正しさは、人が型を決めた見本での選ばせる試験で測る（`docs/ut-reportdeck-types-samples.md`）が、見本は少数で、実案件の曖昧さを覆いきれない。型を導入する前の資料と同じ題材で読み手の評価を比べる確認は、実案件で行う。
- 型の検査は、必須の章の**有無**と件数を見る。「結論の章が事象の説明だけ」「確認の問いが的外れ」は、第三者の理解度テスト（型ごとの追加の問い）で見る。
- 出力先の別の名前の実名版は止めずに注意として報告するだけ（同じ出力先に複数の資料を作れるようにするため）。
