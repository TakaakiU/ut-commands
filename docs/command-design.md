- **記載時点**: 2026-09-14
- **調査対象バージョン**: Claude Code 2.1.270（VS Code 拡張）
- **位置づけ**: `commands/ut-*.md` を作る・直すときの判断基準。

## 1.1 前提: コマンドは skills に統合されている

> Custom commands have been merged into skills. A file at `.claude/commands/deploy.md` and a skill
> at `.claude/skills/deploy/SKILL.md` both create `/deploy` and work the same way.
> Your existing `.claude/commands/` files keep working.

`ut-*` は `.claude/commands/` 形式（旧形式）を使っている。動作は継続するが、
**docs サイトの frontmatter 表は「skills 全般」の表**である。コマンド専用の表ではない。

> A Markdown file in `.claude/commands/` is the older format and still works.
> It supports the same frontmatter except `name` and `paths`.

つまり `name` と `paths` は `.claude/commands/` 形式では使えない。
本書で両方を「不要」としているのは結果的に正しいが、**理由は「不要」ではなく「使えない」**である。

## 1.2 配布経路でフィールドの許容範囲が変わる

⚠️ **Claude Code の中と外で、使えるフィールドが違う。**

| 経路 | 許容されるフィールド |
| --- | --- |
| Claude Code | 表の**全フィールド** |
| Claude Code の外（claude.ai へのアップロード、Skills API、パッケージング） | Agent Skills 仕様の**6つのみ**: `name` / `description` / `license` / `compatibility` / `metadata` / `allowed-tools` |

> If you include any field the spec doesn't allow, packaging or upload fails with a
> **hard error** instead of ignoring the field.

**現行の `ut-*` は Claude Code 外へは出せない。** 使っている
`argument-hint` / `disable-model-invocation` / `disallowed-tools` は仕様の6つに含まれないため、
アップロードは**無視ではなくエラーで落ちる**。

Claude Code 内で使う限り問題はない。将来 claude.ai の personal skill として使いたくなった場合は、
この3フィールドを外すか、別形態を用意する必要がある。
なお `metadata` は6つに含まれるので、`scope` ラベルは経路が変わっても持ち出せる。


## 2. 採用しているフィールド

| フィールド | 適用 | 理由 |
| --- | --- | --- |
| `description` | 全本必須 | 一覧と発見性の要。省略すると本文1行目が使われ、意図と合わない |
| `argument-hint` | 全本必須 | 引数の期待値を利用者に示す |
| `disable-model-invocation` | 全本 `true` | `ut-*` は副作用や長い手順を持つ。モデルの自動起動を許さず、人が明示的に打つものとする |
| `metadata.scope` | 全本必須 | 下記 2.1 |
| `disallowed-tools` | 対象を限定 | 下記 2.2 |

### 2.1 `metadata.scope` — 社内依存の有無

```yaml
metadata:
  scope: generic        # または org-specific
```

| 値 | 意味 |
| --- | --- |
| `generic` | 社内固有のシステム・データに依存しない |
| `org-specific` | 社内固有の仕組み（社内Wiki・製品スキーマ・社内運用フロー）に依存する |

**これは「公開してよいか」という判断ではなく、「何に依存しているか」という性質である。**
公開可否は、上流の作業リポジトリにある公開用の許可リスト（`publish.allowlist`。公開物には含めない）が持つ。両者の関係は等値ではなく片方向の含意になる。
<!-- publish-ref-ok: publish.allowlist 公開用の許可リストは上流の作業リポジトリにだけあり、公開物には含めない -->

> allowlist に載っている → その `scope` は `generic` でなければならない
> （`generic` だが公開しない、はありうる）

`metadata` を使うのは、Claude Code が自前ツール用の自由記述領域として定義しているため。

> Free-form YAML map for your own key-value data ... read by your own tooling from `SKILL.md`.
> Claude Code doesn't act on its contents, and drops a value that isn't a map.

⚠️ 値がマップでないと**黙って捨てられる**。`scope` を直に書かず、必ず `metadata:` の下にネストする。
未定義のトップレベルキーも実機では読み込まれるが、**文書化されていない挙動に依存しない**ため使わない。

### 2.2 `disallowed-tools` — 事故経路を機構で塞ぐ

本文に「実行はしない」「DBへは接続しない」と書いてあるだけの状態は、指示であって機構ではない。
実行禁止を宣言しているコマンドには `disallowed-tools` を付ける。

⚠️ **完全な安全装置ではない。** 公式ドキュメントに明記がある。

> The restriction clears when you send your next message.

塞げるのは「コマンドを起動したそのターン」だけで、会話が続けば元に戻る。したがって:

- ✅ **初手の事故経路を塞ぐ機構**として使う
- ❌ **「このコマンドでは絶対に実行されない」保証**としては書かない

コマンド本文にこの限界を併記する。書かないと読み手が「制限されている」と誤読する。
Codex（`$ut`）ではこのキーは起動したターンでも効かない。そのときの書き方は 2.3 に置く。

付ける対象は「禁止したい事故経路」が具体的に定義できるものに限る。強く付けすぎると、
最小限の調査（ファイルを読む、状態を確認する）まで殺して使い物にならなくなる。

#### 適用状況

| コマンド | 指定 | 理由 |
| --- | --- | --- |
| `ut-plan` | `Bash, Edit, NotebookEdit` | 実行しないコマンド。`Write` は「保存を求められた場合」に使うため残す |
| `ut-sqlpatch` | `Bash, Edit, Write, NotebookEdit` | SQLテキストを生成するだけで、DBへ接続も実行もしない |
| `ut-takeover` | `Edit, Write, NotebookEdit` | 引き継ぎを照合して読むだけで、記載の作業を始めない。`Bash` は照合（部品の `verify`）に要るので残す。Bash 経由の書き込みは本文の決まりと試験（許した呼び出し以外が 0 件）で止める。制限は起動したターンだけ（ID を省いた一覧の後は、選んだ 1 行を打ち直して制限のあるターンで読む） |

| 付けないコマンド | 理由 |
| --- | --- |
| `ut-docrewrite` / `ut-growipost` / `ut-commentrewrite` / `ut-backlogformat` | 既定は dry-run だが `--apply` で実際に書き込む。**同じコマンド内でモードが変わる**ため、ターン単位で効く機構では表現できない |
| その他 | 「禁止したい事故経路」が具体的に定義できていない |

⚠️ **未検証**: 指定したツール名で実際に制限がかかることを実機で確認していない。
ツール名が誤っていた場合、**エラーは出ず、単に何も制限されない**。
そのため各コマンドの本文（§2「前提と、無いときの動作」表・§5）では、Claude Code の側を「止まる設計（実機では未確認）」と書き、「仕組みで止まる」と言い切らない（2026-10-20。リポジトリの中に実機で確かめた記録が無い）。下の確認をして結果をここに書いたら、本文の書き方も合わせて直す。

確認方法: 配備後に `/ut-plan` を実行し `Bash` が拒否されることを見る。
対照として `disallowed-tools` を持たない `/ut-report` では `Bash` が使えることも併せて見る。
**片方だけでは「そもそも Bash を使う場面が無かった」と区別できない。**

### 2.3 Claude Code にしか無い機能に頼るとき

Codex では `$ut`（`codex-skills/ut/SKILL.md`）が `commands/ut-*.md` の本文をその場で読み替えて実行する（`$ARGUMENTS` を `ARGS` に読み替え、環境差は「差分と代替を明示して続ける」）。
本文に、その機能が無いときの動作が書いていなければ、読み替えは実行するモデル任せになる。手順が抜けてもエラーにならず、報告にも出ないので、**抜けても気付けない**。そこで次を守る。

1. 本文が Claude Code にしか無い機能に頼るときは、§2「入力」の「前提と、無いときの動作」表（`### 前提と、無いときの動作` の見出しと `| 前提 | 無いとき |` の表）に 1 行ずつ載せる。機能は次の群で数える（同じ群の機能は 1 行にまとめてよい）。

   | 群 | 含むもの（本文での書き方の例） |
   |---|---|
   | サブエージェント | サブエージェント・subagent・組み込みのエージェント（claude-code-guide など） |
   | セッション間の連絡 | ListAgents・SendMessage |
   | 遅延読み込みのツール | ToolSearch |
   | Web の取得・検索 | WebFetch・WebSearch |
   | 確認の画面 | AskUserQuestion |
   | セッションの切り替え | plan モード・`/model`・`/effort`・`/fast`・`/plan` |
   | 編集の禁止 | frontmatter の `disallowed-tools`（下の 3）。**C20 ではほかの群と扱いが違う**: 本文の語ではなく frontmatter に `disallowed-tools` があるかで見て、表の行は群の名前ではなく `Codex` を含む行があるかで見つける。`c20-ignore` の対象外（外せない） |

   「前提」の列には、やりたいことと、Claude Code での手段を括弧で書く。行には群の名前か、上の書き方のどれかを入れる（C20 はそれで行を見つける）。ただし編集の禁止だけは、群の名前ではなく `Codex` を含む行で見つける（上の表の行・下の 3）。そのため、表の中で `Codex` の語を書くのは編集の禁止の行だけにする（ほかの行にも書くと、編集の禁止の行を消しても C20 が気付かない。試験 T48f が見ている）。ほかの行で Codex の場合を書くときは「`$ut` から呼んだとき」と書く。

2. 「無いとき」の列には、次をすべて書く。「適宜」「可能なら」で終わらせない。
   - **動作を 1 つに決める**: 代わりの手順で続ける／何を省いたかを報告して続ける／止まる、のどれか。
   - **代わりの手段は、元の手段より権限・副作用（書き込み）・外への開示（送信や、マスクを通らない経路）・費用（追加の導入・課金）を増やさないときだけ使う。** どれかが増えるなら、止めて利用者に確かめる。同じ以下にできなければ、省くか止まる。
   - **途中で止まる・省くときに残る状態**（`.partial`・下書き・一時ファイル・作業フォルダ）と、その場所・後始末・再開の仕方、完了として扱うか。始める前に無いと分かるものは、始める前に確かめて止まる（途中まで進めない）。

3. `disallowed-tools` で止めている制限は、Codex では仕組みで止まらない（`$ut` はこのキーを解釈しない）。Codex では**本文の決まりという弱い保証に下がり**、2.2 の機構と同じ強さではない。そこで:
   - 本文の禁止事項（§5）にも同じ制限を書く（何を作らない・編集しない・起動しないか）。
   - 表に Codex（`$ut`）の行を足し、仕組みでは止まらず本文の決まりだけで守ること（弱い保証であること）を書く。Claude Code 側の「制限されている」を、Codex にそのまま当てはめない。

4. `$ARGUMENTS` と、Read・Edit・Bash など道具の名前で書く手順はそのままでよい（`$ut` が `ARGS` に読み替え、Codex のモデルは同じ役割の道具を使う）。結果が変わる差だけを注記する（例: Windows の Bash は Git Bash で、`/` で始まる引数が `C:/Program Files/Git/…` に書き換わる）。

5. 次の手順として利用者に打ち直させる 1 行（`/ut-<名前> …`）は、Codex では `/ut-…` を打っても `$ut` が起動しない。Codex での形（`$ut CMD=ut-<名前> ARGS="…"`。`ARGS` の値の中に `"` は書けない）を、その機能の行に「`$ut` から呼んだとき」として書く（例: `ut-takeover` の候補の 1 行、`ut-handoff` のクリップボードの 1 行）。`Codex` の語は、上の 1 の決まりどおり編集の禁止の行だけで使う。書いていないときは `SKILL.md` の手順 6 が同じ形に直す。本文の例の行（`/ut-…`）はどのコマンドにもあって語では見分けられないので、C20 の群には入れず、レビューで見る。

Codex の側で、元のコマンドの決まりとラッパーの一般の代わりが食い違うときの順番（①禁止事項 ②この表に書いた動作〔止まる・省く・決めた代わりの手順で続ける〕 ③frontmatter の制限 ④一般の代わり）は、`codex-skills/ut/SKILL.md` の「従う順番」に書く。表が決めた代わりの手順（読み取りだけのシェルなど）は、③の読み替えと④より上に置く（表の Codex の行が Codex での読み替えの正本）。止める条件は、上の 2 の 4 つ（権限・副作用・外への開示〔マスクを通らない経路を含む〕・費用）を `SKILL.md` にも同じ言葉で書く。4 つを比べる基準は、表が決めた代わりの手順ではその手順自体、ラッパーの一般の代わりでは元のコマンドの通常手順とする。

機械で見るのは C20（§4）。見るのは「本文に群の語があるのに、表にその群の行が無い」ことと、「`disallowed-tools` があるのに、表に Codex の行が無い」ことだけで、書いた動作が妥当か（1 つに決まっているか・権限などを増やさないか・残る状態を書いたか）はレビューで見る。
否定・比較・説明だけで語を書いた所（例: 機能を切る設定の説明、例の文に出る設定の名前）は、本文に `<!-- c20-ignore: <群の名前> <理由> -->` を 1 行で書いて、その所の語を外す（理由が空なら外さずに警告する）。

- **効く範囲**: 注記を書いた行と、その直前・直後の 1 行（空の行も 1 行と数える）にある、その群の語だけ。ファイル全体からは外さない（後から同じファイルに本当に頼る手順を足したときに、黙って通さないため）。
- **置き場所**: 語のある行の直後の行か、同じ行の末尾に書く。表や箇条の途中では、注記だけの行を挟むと表・箇条が切れるので、同じ行の末尾（表なら最後の `|` の前）に書く。
- 範囲の中にその群の語が無い注記は、何も外していないので警告する（置き場所の誤りや、語を消した後の残り）。
- 注記の中の語（理由の文に出る別の群の語など）は数えない。
- 編集の禁止（`disallowed-tools`）は外せない。

出所: 社内の Claude Code プラグインの考え方（機能ごとに、無い環境での代わりを書く）を参考にし、ut-commands の既存の「前提と、無いときの動作」表に寄せて決めた（2026-10-20）。

## 3. 採用していないフィールド

| フィールド | 判断 | 理由 |
| --- | --- | --- |
| `allowed-tools` | 見送り | 事前承認（許可を広げる側）。`ut-*` は確認を挟む設計なので、許可を先回りで広げる動機が無い |
| `model` / `effort` | 保留 | 機械的な処理なら軽量モデルで足りるが、設計判断・レビュー・引き継ぎ生成を安くすると品質が落ちる。対象を特定してから入れる |
| `context: fork` / `agent` | 保留 | 重い収集には効きうるが、挙動の理解コストが上がる。「遅い・文脈を汚す」実害が特定できてから |
| `` !`command` `` / `@file` | 採用しない | 実行前に文脈を注入できる反面、**失敗するとコマンド全体が中断する**。環境差で壊れやすい |
| `arguments`（名前付き引数） | 次段階 | `$ARGUMENTS` を本文で解釈するより誤用が減る。既存15本の引数仕様を一度に変えるのは別作業 |
| `license` / `compatibility` | 次段階 | Agent Skills 仕様。Claude Code は受け取るが何もしない。公開する分に入れる価値がある |
| `user-invocable` | 不要 | `ut-*` はすべて人が打つもの。既定（`true`）でよい |
| `paths` | **使えない** | `.claude/commands/` 形式では対象外（skills ディレクトリ形式なら使える） |
| `hooks` / `shell` | 不要 | 現状そこまでの制御を必要としていない |
| `when_to_use` | 不要 | 全本 `disable-model-invocation: true` で自動起動しないため、効く場面が無い |
| `name` | **使えない** | `.claude/commands/` 形式では対象外。コマンド名はファイル名で決まる |

### Codex 側（skills）で自動の起動を止める

Codex の入口（`codex-skills/<名前>/`）でも、ut-* は「人が明示したときだけ動く」方針を保つ。
ただし Codex の `SKILL.md` は `disable-model-invocation` を解釈しない（openai/codex#29989、2026-09-30 時点で未解決）。
代わりに skill のフォルダの `agents/openai.yaml` に `policy.allow_implicit_invocation: false` を書く（https://learn.chatgpt.com/docs/build-skills ）。

| 確認 | 結果（2026-09-30、Codex 0.154 の実機） |
|---|---|
| 何も書かない | 内容に合う依頼で 3/3 回、自動で起動した |
| `allow_implicit_invocation: false` | 同じ依頼で 0/3 回。`$名前` と明示すれば起動した（陽性対照）。一覧からも見えなくなった |

この設定の止め忘れは `deploy.mjs` の C13 が止める（`--no-check` でも迂回できない）。
ただし C13 が見るのは「決めた形と一致するか」だけで、**Codex がこの設定を読むかどうかは見ていない**。
Codex の版上げでキーの名前や扱いが変わると、エラーを出さずに自動で呼ばれるように戻る。版上げのたびに下の「5. 再確認の手順」で実機の試験をやり直す。

**止められるのは「Codex が skill を自動で読み込んで従うこと」まで**で、モデルが自分でシェル（`rg`・`Get-Content` など）を使ってファイルを探し、読むことは止められない。
実機でも、「ut-handoff 相当の引き継ぎを作って」のような依頼では、skill は起動しなかった（`UT_SKILL:` の行が出ない）一方で、モデルが `~/.claude/commands` やリポジトリを探して元のコマンドを読んでいた（2026-09-30）。
これは移行の前から同じ（読み取りの sandbox でもホームの下は読める）。人が明示したときだけ**決まった手順で**動く、という点は skill の設定で守られる。

ut-defer の無人実行と同じ起動引数（`--ignore-user-config` など）でも、ユーザー単位の skills（`~/.agents/skills`）は見える。
実機では、明示すれば起動し（陽性対照）、自然な依頼 3 件では起動しなかった（2026-09-30）。
起動したかの判定は、最終返答の `UT_SKILL:` の行ではなく、実行の記録で「最初に `~/.agents/skills/<名前>/SKILL.md` を読んだか」で見る。
`UT_SKILL:` の行は、明示して起動した場合でも書き忘れることがあった（補助にとどめる）。

### `description` の長さ

一次情報の上限は次のとおり。

> the combined `description` and `when_to_use` text is truncated at 1,536 characters

現行15本の最長は `ut-commentrewrite` の285バイト（95文字）で、上限に対して十分収まっている。**短縮は不要。**
（二次情報に「60字目安」とあるが、一次情報の値ではない）

## 4. 機械的に守られること

人の記憶ではなく `deploy.mjs --check` が見る。

| 検査 | 内容 |
| --- | --- |
| C2 | `ut-*.md` が6節骨格を順序どおり持つ |

## 5. 再確認の手順

本書の内容はバージョンに依存する。次のいずれかのときは引き直す。

1. Claude Code のバージョンが上がり、frontmatter 関連の挙動が変わったと疑うとき
2. **Codex のバージョンが上がったとき**（skills の自動の呼び出しを止める設定が効くかを、実機で確かめ直す。確認済みの版: 0.154）
3. 新しいフィールドを使いたくなったとき
4. 本書の記載と実挙動が食い違ったとき

手順:

1. **docs サイトの frontmatter 表を引く**（GitHub 側は部分集合なので単独で使わない）
2. 使いたいフィールドが**文書化されているか**を確認する。文書化されていない挙動に依存しない
3. 挙動を変えるフィールドは、**対照を用意して実機で確認する**。
   「壊したときに落ちること」まで見る（通ることは根拠にならない）
4. 本書を更新する。**採らなかった理由も残す**

Codex の自動の呼び出しの試験（版上げのたびに行う）:

1. 一時フォルダに `.agents/skills/probe/SKILL.md`（`description` に話題を書き、本文で決まった文字列だけを返させる）を置く
2. `agents/openai.yaml` 無しで、話題に合う依頼を3回出す → 決まった文字列が出る（自動で起動する＝陽性）
3. `agents/openai.yaml`（`allow_implicit_invocation: false`）を置いて、同じ依頼を3回出す → 出ない（陰性）
4. `$probe` と明示して呼ぶ → 出る（明示の呼び出しが効く陽性対照）
5. 結果と Codex の版を、本書の「Codex 側（skills）で自動の起動を止める」の表に書く

## 6. コマンドの名前

名前の付け方は、既存のコマンド名から帰納した傾向を規則として書いたもの（2026-10-09）。

- コマンド名は `ut-` ＋ 英小文字の短い語を基本とし、語は連結する。ハイフンは、製品名を含むなど重大な誤読を避ける場合だけの例外とする（例: `ut-vscode-debug`）
- 対象領域がある場合は `ut-<対象領域><主要動作または主要成果物>` とする（例: `ut-alertcollect`、`ut-sqlpatch`）
- 同じ系列は対象領域の語をそろえ、同じ動作語を別の意味で使わない。系列の入口は対象データを変更しない
- 対象を限定しない汎用のコマンドは、単独の動作・成果物の名前を許す（例: `ut-plan`、`ut-handoff`）
- Claude Code の組み込みコマンド・Windows の標準コマンド・主要な CLI の語との衝突を確かめる（例: `compact` は `/compact`・`compact.exe`・diskpart の `compact vdisk` と衝突する）。元に戻せない操作をするコマンドは、名前と `description` の先頭で既定の動作を明示する

同じ語を範囲の違う別の場所で使うのは許す。「同じ動作語を別の意味で使わない」は意味の違いを止める規則で、範囲の違いには当たらない。例: `ut-review` は組み込みの `/review`（PR 用）・`/ut-defer` の `review` サブコマンドと同じ語だが、「対象を見て問題を確かめる」という核の意味は同じで、対象の範囲だけが違う。打つ名前は `ut-` が付いて別になり、サブコマンドは補完の候補に並ばない。範囲の違いで誤って打たれうる場合は、`description` の先頭で打ち消す（理由の詳細は `docs/ut-review.md`）。

対になる 2 本は、役割（向き）が語から読める対にする。例: `ut-handoff`（渡す）と `ut-takeover`（引き取る）。`handover` は渡す側の語で役割が逆に読め、`ut-hand…` の補完で `ut-handoff` と並んで選び間違えやすいので採らなかった（比較は `docs/ut-handoff.md`）。

機械で守れるのは名前の**形**（C15）と、やめた名前の使い直し（C16）だけで、「対象領域と動作の並び」「系列で語をそろえる」は語の切れ目を機械で決められないため、レビューで見る。

### 6.1 やめた名前

やめた名前を別の意味で使い直すと、記事・メモ・利用者の記憶に残った古い意味で打たれる。使い直すときは理由を書く（書かずに使うと C16 が止める）。

| 名前 | やめた日 | やめた理由 | 使い直しの理由 |
|---|---|---|---|
| `ut-diskclean` | 2026-09-10 | `ut-diskreport` へ改名した（6d9680960）。clean は実行系に読め、既定がレポートであることと食い違っていた | 2026-10-09、ディスク系を入口（`ut-diskreport`）と出口（削除・圧縮）に分けたとき、削除専用の出口の名前として使い直した。削除だけを受け持つので、やめた理由（既定がレポートであることとの食い違い）は当てはまらない |

## 7. 不可逆・外部操作を持つコマンドの最低ライン

コマンドごとに本文の長さや仕組みの厚みが違う（2026-11-20 の調査: 本文は 48〜244 行。節は `ut-growipost` 以外すべて 6 節）。
**行数や節の数は品質を決めない**ので、揃えない。差が実害になるのは、**復元できない操作を持つのに、防御が手順書の文章だけ**のときである。

### 最低ライン

| 対象 | 求めること |
|---|---|
| 復元できない操作（削除・上書き・外部への書き込み）を持つ | 判定が機械でできる部分（パスの境界比較・リンクの扱い・計画との照合・直前の再測定など）を部品（`tools/*.mjs`）に切り出す。部品に `--selftest` を持たせ、防御を 1 つずつ壊して落ちるかを見る掃引（`*-sweep.mjs`）を付ける |
| 上記のうち既定が読み取り・dry-run のもの | 実行は明示の指定（`--apply` など）と、会話での確認の両方が揃ったときだけ。確認の有無は部品からは見えないので、確認を取る責任は本文（モデル）に書く |
| 操作を持たない、または出力が人のレビューを通るもの | 手順書の文章だけで守ってよい（`ut-sqlpatch` のように、出力を人が読んでから実行するもの） |

### 現状（2026-11-20）

| コマンド | 不可逆・外部操作 | 防御の作り |
|---|---|---|
| `ut-diskclean` | 削除 | 部品 `tools/ut-clean.mjs`（scan・apply）と掃引。**以前は手順書だけで、毎回モデルが削除の判定を組み立てていた**。2026-11-20 に部品化した |
| `ut-diskarchive` | 解放は明示指定のみ（元は消さない） | 部品 `tools/ut-archive.mjs` と掃引 |
| `ut-growipost` | GROWI への書き込み | 既定は dry-run。`tools/growi-mcp` に掃引 |
| `ut-docrewrite`・`ut-commentrewrite`・`ut-backlogformat` | `--apply` でファイルを上書き（`ut-backlogformat` は出力ファイル） | **部品なし**（照合は手順書の指示。`ut-commentrewrite` のコメント除去後のバイト一致照合などを、モデルがその場で組み立てる） |

### 未対応と、判断の根拠

- `ut-docrewrite`・`ut-commentrewrite`・`ut-backlogformat` は、上書きの前の照合（バイト一致・本文の欠落）を部品にしていない。ただし `ut-docrewrite` と `ut-commentrewrite` は、**上書きの前に元のファイルを退避し、書き込み後に再読して検証する**ことを本文で求めている（復元の経路がある）。`ut-backlogformat` は投稿せず、元のファイルを上書きしない。`--out` が既存のファイルを指すときも、2026-11-20 に本文へ「上書きせず確認する（明示された場合だけ、退避してから上書き）」を足した（それまでは本文から読み取れなかった）。
- この調査は構造の推定で、**コマンドごとの成果の差を測っていない**。実害の記録も見つけていない。
- 覆す条件: 手順書だけで守っているコマンドで、照合の抜けによる実害（意図しない上書き・欠落）が出たら、そのコマンドの照合を部品にする。

### 採用: `ut-review` の読み取り専用サブエージェントを Agent 定義にした（2026-11-20）

`/ut-review` は、読み取りだけのサブエージェントを「指示文の約束」で使っている（実行時は汎用のサブエージェントに、道具の制限をかけずに渡している）。仕組みで縛る案として、Agent 定義（`~/.claude/agents/*.md`）を調べた。公式文書（https://code.claude.com/docs/en/sub-agents.md。約 11.6 万字のうち先頭 10 万字まで読んだ）で確認できたこと:

- frontmatter に `tools`（許可リスト）と `disallowedTools`（拒否リスト）があり、`tools: Read, Grep, Glob` の形で読み取り専用にできる。両方あれば拒否リストを先に当てる。
- `~/.claude/agents/` に置けば、どのプロジェクトからも使える。`model` と `permissionMode` も指定できる（親が `bypassPermissions`・`acceptEdits`・`auto` のときは、親のモードが優先される）。

**確認できていないこと:** 道具の制限が「仕組みで強制される」とは、文書が明言していない。親の制限をサブエージェントが超えられるかも未確認。`subagent_type` で名前指定する書式の全体も未確認。

見送っている理由: 採るなら、(1) `deploy.mjs` が `~/.claude/agents` を配備できるようにする、(2) `ut-review.md` を名前指定の呼び出しに直す、(3) 強制の有無を実機で確かめる（制限した道具で書き込みが拒否されることと、対照として制限しない定義では書けること）が要る。強制の有無が未確認のまま「仕組みで縛った」と書くと、`disallowed-tools` と同じく読み手を誤解させる（§2.2）。**実機確認（3）を先にやる。** 覆す条件: 実機で拒否されることが確認できたら、採る。

**実機確認（2026-11-20、Claude Code 2.1.284、`claude -p` と `--agents` で定義を渡し、一時フォルダで実行）:**

| 定義 | 道具 | 書き込みの試み | 結果 |
|---|---|---|---|
| `probe-ro` | `Read, Grep, Glob` だけ | Write・Bash で `ro.txt` を作らせた | **作れなかった。** 自己申告の道具も `Read, Grep, Glob` のみ。ファイルは実在しない |
| `probe-rw`（対照） | 指定なし | 同じ依頼で `rw.txt` を作らせた | 作れた（`Write`・`Bash` などを持つ。ファイルは実在） |
| `probe-file-ro`（ファイルの定義。一時フォルダの `.claude/agents/`） | `Read, Grep, Glob` だけ（frontmatter の `tools`） | 同じ依頼で `fro.txt` を作らせた | **作れなかった。** 自己申告の道具は `Read, Grep, Glob` のみ。ファイルは実在しない |

道具の制限は、少なくとも名前指定の呼び出しでは、**道具そのものをサブエージェントから外す形で効いた**（`disallowed-tools` のように「効かないかもしれない」状態ではなかった）。ただし、確かめたのはこの経路だけである。
- ファイルの定義はプロジェクトの `.claude/agents/` で確かめた。ユーザーの `~/.claude/agents/` に置いた定義では確かめていない（読み込みの経路は同じ文書の記載だが、実機では未確認）。
- 呼び出し元の親が `bypassPermissions` などのときの挙動は確かめていない。
- 実際の `/ut-review` の指示文から呼ぶ形では確かめていない。

**採用した形:** `agents/ut-review-reader.md`（`tools: Read, Grep, Glob`）を `deploy.mjs --target claude-agents` で `~/.claude/agents/` へ配備する。`ut-review.md` は、定義があれば `subagent_type` にその名前を指定して呼び、無ければ汎用のサブエージェントで代える（この場合は指示文の約束で、仕組みでは止まらない）。`deploy.mjs --check` の C21 が、定義の `tools` が無い・読み取り以外の道具を含む・制限の意味を変えるキー（`permissionMode`・`hooks`・`mcpServers`・`disallowedTools` など）がある場合にエラーにする（`tools` が無いと全部の道具を継承し、制限が黙って外れるため）。
