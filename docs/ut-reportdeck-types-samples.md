# 資料の型の選び方を測る見本

`commands/templates/ut-reportdeck-guide.txt` の §0（型の選び方）が、狙いどおりに型を選べるかを測るための見本。題材はすべて架空。
測り方: 答えを伏せた状況の一覧と §0 だけを、別のサブエージェント（読み取りだけ）に渡し、各状況について「型・理由・迷いの有無」を答えさせる。答えと比べる。

| ID | 状況（要旨） | 期待する型 |
|---|---|---|
| S1 | 夜間の配信ジョブの停止。何が起き、なぜで、何をするかを上長に報告 | 障害・不具合 |
| S2 | 3 つの方式から採る方式を部長に決裁してもらう | 決裁・提案 |
| S3 | 問い合わせ増加の理由を調べ、分かったことと未確認を共有 | 調査報告 |
| S4 | 新任が仕組みを理解し、止まったとき自分で調べられるようにする | 読本・解説 |
| S5 | 画面の表示崩れの経緯・原因・修正を会議で説明 | 障害・不具合 |
| S6 | 新ツールの導入可否を、費用と効果の比較で決めてもらう | 決裁・提案 |
| S7 | 性能劣化の原因は特定できず、候補と次の測定計画を共有 | 調査報告 |
| S8 | 運用担当が障害を切り分けられるよう、データの流れを教える | 読本・解説 |
| S9 | 障害の再発防止策 A／B のどちらで進めるかを上長が決める | **迷う**（決裁・提案か障害・不具合。候補 2 つを並べるのが正しい） |
| S10 | 新機能の仕様の調査結果を、新人研修にも使いたい | **迷う**（調査報告か読本・解説。候補 2 つ。混ぜない） |
| S11 | 月次の利用状況の分析を共有（判断を求めない） | 調査報告 |
| S12 | 他社事例を調べたうえで、自社が採る方式を提案し承認をもらう | 決裁・提案 |

期待の置き方: S9・S10 は、2 つの型にまたがるので「迷うと言い、候補を 2 つ出すこと」を正解とする（1 つに決め打つのは不正解）。S12 は調査を含むが、承認を求めるので決裁・提案。

## 結果の記録
測るたびに、日付・使ったモデル・正解数（明確な 10 件）・S9／S10 で迷いを出せたか・外した状況の理由を、ここに追記する。

### 2026-11-11（1 回目。手引き §0 の初版）
- 使ったモデル: 本作業と同じ系統のサブエージェント 1 本（読み取りだけ）。見本は答えを伏せて渡した。
- 明確な 10 件（S1〜S8・S11・S12）: **10 件中 10 件が期待どおり**。S9・S10 は「迷い: あり」と第 2 候補を出せた（S9 は第 1 候補が決裁・提案、第 2 が障害・不具合。S10 は第 1 が読本・解説、第 2 が調査報告。いずれも期待の 2 型に収まる）。S7 は型は合ったが「迷い」を出した（原因が未特定の障害調査の扱いが手引きに無かった）。
- 規則の曖昧な点として挙がったもの 4 件（S7 原因未特定・S9 経緯の置き場・S10 兼用・S12 調査と提案の混在）を、手引き §0 に「境目の扱い」として追記した。**追記後の再測定はまだ**（同じ見本で測ると見本に合わせた書き方になるので、新しい見本を作って測る）。
- 限界: 同系統のモデルで、見本は作成者（同じ系統）が書いた 12 件。実案件の曖昧さは覆えない。

- 1 回目の追記は効いた（N2・N3・N4・N6 は、追記した「境目の扱い」の文を引いて決まった）。一方で、見本を変えるたびに、別の曖昧な点が 3〜4 件ずつ出ている。型の選び方は、実案件で迷った例を足しながら育てる前提で、利用者が構成表で承認する手順が最後の砦になる。
