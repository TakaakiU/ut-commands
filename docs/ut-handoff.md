# /ut-handoff と /ut-takeover — 設計の理由と限界

`/ut-handoff` は引き継ぎを作り、`/ut-takeover` は新しいセッションでそれを照合してから読み込む。
以前は、`/ut-handoff` が出した貼り付けブロックを新しいセッションへ手でコピペしていた（2026-10-16 に変更）。

## 何を変えたか
| | 以前 | 今 |
|---|---|---|
| 新しいセッションでの操作 | 長いブロックを選んでコピー → 貼り付け | 新しいセッションを開いて Ctrl+V → Enter（`/ut-takeover <ID>` の 1 行がクリップボードに入っている） |
| 取り違えの防ぎ方 | 人が確かめる | リポジトリ・ブランチが違う、HEAD が祖先でない、同じリポジトリ・ブランチにより新しい引き継ぎがある、のどれかなら止める（git の外なら作った場所が違えば止める。リポジトリで作ったものを git の外で読むときは、`--accept-…` でも続けず貼り付けブロックを案内する）。HEAD が進んだだけ・作業ツリーが違うだけなら警告して続ける |
| 画像・資料 | セッションの一時フォルダに残り、後で消えうる | 引き継ぎのフォルダの `files/` に写し、一覧を付ける |
| 読み込みの扱い | 貼った文がそのまま利用者の発言になる | `/ut-takeover` が読み、中身はデータとして示す。Edit・Write を止める設計（実機では未確認。`docs/command-design.md` §2.2） |
| 完了の確かめ方 | なし | 作成元のセッションに受領通知が届く |

貼り付けブロックは今も必ず出す（`/ut-takeover` が使えない環境の代わり）。

## 方式を選んだ理由
### セッション間の連絡で本文を送らない
Claude Code のセッション同士は ListAgents・SendMessage で連絡できる。最初はこれで引き継ぎ文を新しいセッションへ送ることを考えたが、採らなかった。
- 開いただけで一度も入力していないセッションは、宛先の一覧に出ない（2026-10-16 に実機で確認）。そのため、新しいセッションでの入力は 1 回残る。その 1 回を `/ut-takeover <ID>` にすれば、本文を送らなくても同じことができる。
- 届いたメッセージは利用者が入力したプロンプトと同じく使用量に数えられ、待機中の受け手では新しいターンが始まって会話全体が送られる。
- 連絡は文字だけで、画像・ファイルは送れない。資料はどのみちファイルで渡す必要がある。
- 届くと受け手が利用者の操作なしに動き出す。読み込みは利用者が打ったコマンドで始まる方が、何が起きたかを追いやすい。

連絡機能は、読み込みが済んだことを作成元へ知らせる短い受領通知にだけ使う（下の「費用」）。

### クリップボード方式（リンクは試験的）
VS Code 拡張機能には `vscode://anthropic.claude-code/open?prompt=…` で新しいタブを入力済みで開くリンクがある、と文書にある。これなら Enter だけになるが、2026-10-16 にこの環境で 3 回試してタブが開かなかった（拡張機能の処理と `vscode://` の登録はあることを確かめた）。開いたかどうかを作る側から判定する手段も無い。
そのため既定はクリップボード方式にし、リンクは `--open` を付けたときだけの試験的な扱いにした。

### 別コマンドにした（入口の名前の比較）
読み込む側をサブコマンドではなく別のコマンドにしたのは、`disallowed-tools` で Edit・Write を止める設計にできるから（同じコマンドの中でモードが変わるものには付けられない。実機で止まることは未確認＝`docs/command-design.md` §2.2）。
| 候補 | 形 | 命名規則（§6） | 紛らわしさ | 書き込みを仕組みで止める | 今の引数とのぶつかり |
|---|---|---|---|---|---|
| `/ut-takeover`（採用） | 別コマンド | 単独の動作の名前で可。`handoff`（渡す）と対で役割が読める | 組み込み・Windows の標準コマンドと衝突しない。`ut-hand` で始まる補完で並ばない | 止める設計（Edit・Write。実機では未確認。`docs/command-design.md` §2.2） | 無い |
| `ut-handon`（採らなかった） | 別コマンド | 造語 | `/ut-handoff` と 1〜2 文字違いで補完でも並ぶ。打ち間違えると作る側が動く | 止める設計にできる（実機では未確認） | 無い |
| `ut-handover`（採らなかった） | 別コマンド | 渡す側の語で、役割が逆に読める | `/ut-handoff` とほぼ同じ意味の語で、補完でも並ぶ | 止める設計にできる（実機では未確認） | 無い |
| `/ut-handoff load` | サブコマンド | 可 | 少ない | **できない**（文の決まりだけ） | ある（`/ut-handoff load test の調査` が読み込みに化ける） |
| `/ut-handoff pickup` | サブコマンド | 可 | 少ない | **できない** | ある |
組み込みの `/resume`（古い会話を丸ごと読み込む高い操作）と同じ語は、どの候補でも避けた。

### 照合の値を HMAC にした
見出しにリポジトリのパス・ブランチ名・セッション名をそのまま書くと、顧客名などがパスや名前に入っていた場合に残る。塩の無いハッシュも、候補の少ない値は総当たりで戻せる。
そこでマシンごとの秘密（`<保存先>/.key`）を鍵にした HMAC にした。照合は同じマシンの中だけなので、鍵を共有しなくてよい。鍵を作るのは `/ut-handoff` だけで、`/ut-takeover` は作らない（鍵が無いのに作ると、すべての照合が「違う」になり、原因を取り違えるため）。

## 費用
- 新しいセッションでの最初のターンの固定分（システムプロンプト・CLAUDE.md・メモリ）は、コピペで始めた場合と同じ。読み込む量は再開用ブロックだけで、詳細版の全文は読まない。
- 受領通知は 300 文字以下の 1 通だけ。ただし作成元のセッションが待機中なら、その会話全体を送る 1 ターンが走る。作成元の会話が長いときは `/ut-handoff --no-notify` で通知を受けない。

## 検証
- `node commands/templates/ut-handoff.mjs --selftest`: ID と保存先の外を指す指定、鍵（作るのは create だけ）、生の値を書かないこと、照合（リポジトリ・ブランチ・切り離し・HEAD・作業ツリー・より新しい引き継ぎ・旧形式・鍵の違い）、候補の絞り込み、資料の写しと除外、書く順序と段ごとの失敗、ポインタの失敗と同時作成、後片付け、受領通知の文面、クリップボード（1 行の形の検査・読み戻し・CLI の `--id` と `--text`・知らないオプション。Windows で Git for Windows の bash があれば、実際に Git Bash を通して `/` の変換が起きることと、`--id` なら壊れないことも確かめる）。日本語と括弧を含むパスで試す。
- `tools/ut-handoff-sweep.mjs`: 防御を 1 つずつ壊し、その防御を見る試験が落ちるかを確かめる。

## 限界
- **Bash 経由の書き込みは仕組みでは止まらない。** `/ut-takeover` で止まる設計なのは Edit・Write だけ（実機では未確認）で、Bash は照合に要るので残る。本文の決まりと試験で止めている。この制限が効くのも起動したターンだけ（ID を省いて一覧を出したときは、選んだ 1 行を打ち直してもらい、制限のあるターンで読む）。
- **作業ツリーの状態は、親リポジトリの見え方で取る。** サブモジュールの中の未コミットの変更は中身まで見ない（種類だけ）。状態を取れなかったときは「照合できない」と警告する。
- **本文の機微値は型でしか止めない。** 部品は下書きに機微値の型（鍵の代入・トークン・メールアドレス・IP アドレスなど）が当たれば保存を拒むが、型に無い顧客名などは LLM がマスキング基準で伏せる。
- **同じ引き継ぎを二度読み込める。** 読み込んだ印を書かない（`/ut-takeover` は何も書かない）ため。ID を省いたときは自動で選ばず一覧から選ばせる。
- **画像は中身を確かめない。** 画面の写しに顧客名などが映っていても写る（「マスク未確認」の印を付け、作る側の報告に一覧を出す）。引き継ぎのフォルダを人に渡す前に確かめる。中身を確かめられないそれ以外の形式は、既定で写さない。
- **2 つのセッションが同時に作ると、ポインタは後から書いた方を指す。** `/ut-takeover` は ID で読むので影響を受けない。
- **鍵を失うと、過去の引き継ぎは照合できない。** `--accept-legacy` で照合を省いて読む。
- **連絡用の名前はタブの名前ではない。** ListAgents の名前（自動で付く `<フォルダ名>-NN` など）は VS Code のタブにも会話の記録にも出ず、利用者はどのタブのことか分からない（実機の試験で「ut-commands-04 のタブ」と案内して聞き返された）。両コマンドとも利用者向けには引き継ぎ ID と役割（作成元／引き継ぎ先）で示し、名前は括弧の補足だけにする（§4「セッションの示し方」。`deploy --check` の C19 が、両方の本文に同じ文があることを見る。書き手が守るかは実機の試験で見る）。
- 受領通知が届いたことは「受信箱に入った」だけで、読まれたこと・同意されたことではない。Codex など連絡機能が無い環境では通知しない。
- **VS Code の拡張機能では、タブを閉じても（アーカイブしても）作成元のセッションは終わらない**（2026-10-16 の実機。プロセスが残り、ListAgents にも idle のまま出る）。このとき受領通知は画面に出ていないセッションの受信箱に入り、作成元が 1 ターン動く。通知を送らないのは、作成元のプロセスが終わって一覧から消えたときだけ。
- クリップボードは上書きされる（作る側の報告に書く）。クリップボードの道具が無い環境では、表示した 1 行を打つ。
- **1 行はシェルを通さずに組み立てる（2026-10-19）。** Windows の Claude Code では Bash ツールが Git Bash で、ネイティブの exe に渡す引数のうち `/` で始まるものを Unix のパスとみなして書き換える（`/ut-takeover <ID>` → `C:/Program Files/Git/ut-takeover <ID>`。`--base "C:\…"` が入ると `:` を区切りとみなし、`;`・`\` まで変わる）。以前の手順は `clip --text "<1 行>"` で渡していたため毎回壊れ、部品は検査せずに入れて `ok: true` を返していた（エラーを出さずに失敗する型。別のセッションの実機で、貼り付けて初めて気づいた）。今は手順を `clip --id <ID> [--base <保存先>]` にし、1 行は部品の中で組み立てる（シェルを通るのは ID とパスだけで、パスは変換されても正しい形のまま）。手で打つ人のために `--text` は残し、形（`/ut-takeover <ID> [--base "<絶対パス>"]`）に合わなければ入れずに理由を返す。`MSYS_NO_PATHCONV=1` を手順に書く案は採らなかった（`--base` の `/c/…` の変換まで止めてしまい、人が守る決まりになる）。
- **Windows は PowerShell の `Set-Clipboard` で入れ、書いた後に読み戻して確かめる。** 値は Base64 で渡し、PowerShell の中で UTF-8 から戻す（文字コード・引用符に左右されない）。clip.exe は標準入力をコンソールのコードページで読み（日本語が化ける）、BOM を付けた UTF-16LE で渡すと BOM を文字として残す（2026-10-19 の実機で、読み戻しの照合がこれを見つけて止めた）ので、PowerShell が使えないときの予備にとどめる。読み戻しは `Get-Clipboard` で、違えば失敗にする。読み戻す道具が無ければ `verified: false`（入れたが確かめていない）を返す。PowerShell の起動の分だけ 1〜2 秒ほど遅くなる。
